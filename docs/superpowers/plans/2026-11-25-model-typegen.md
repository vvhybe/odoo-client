# 0.3.0 Model Type Generator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.3.0 of `@vvhybe/odoo-client`. It adds a model type generator: a function, and a `typegen` command that writes TypeScript interfaces from `fields_get`. It is published to npm through trusted publishing and to GitHub Packages.

**Architecture:**
- A pure generator in `src/typegen/generate.ts` maps a `fields_get` result to interface source.
- A testable command in `src/typegen/command.ts` parses the arguments and environment, connects with `OdooConnect`, and writes the file.
- `src/typegen/cli.ts` is the two-line bin entry.
- A separate `publish-github` job adds GitHub Packages.

**Tech Stack:** TypeScript (ESM), Node ≥ 18 built-ins (`node:util` `parseArgs`, `node:fs/promises`, `node:path`), vitest, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-25-model-typegen-design.md`

## Global Constraints

- No new runtime dependencies. Node built-ins only.
- Output is deterministic: no timestamp, URL or database name; fields sorted by name; models in the order given; LF line endings and a trailing newline.
- The header line is exactly `// Generated by @vvhybe/odoo-client typegen — do not edit by hand.`
- Credentials come only from `ODOO_URL`, `ODOO_DB`, `ODOO_USERNAME`, and `ODOO_PASSWORD` or `ODOO_API_KEY`, plus optional `ODOO_VERSION`. They are never read from argv and never printed.
- Exit codes: 0 on success, 1 for a usage error or missing variable, 2 when Odoo fails. Never print a stack trace.
- The type mapping is the spec's table, verbatim.
- `fields_get` attributes: `["type", "string", "relation", "selection"]`.
- Commits follow Conventional Commits (commitlint). The husky hooks run lint, format check, typecheck, tests and build.
- The trusted publisher expires unless 0.3.0 publishes before **2026-11-27 11:48 UTC**.

## Review Focus

1. **A model name with a typo:** `fields_get` fails in Odoo. The command must exit 2 with Odoo's message, and must not write a partial or empty `--out` file. Covered in Task 2.
2. **Selection keys that are not plain identifiers** (`"on_hold"`, `"two words"`, `"it's"`, integer keys): they become valid TS literals through `JSON.stringify`. Covered in Task 1.
3. **A label containing `*/`:** it must not close the doc comment early. It is escaped as `*\/`. Covered in Task 1.
4. **A selection with an empty list** (dynamic selections can return `[]`): the type is `string | false`, not a bare `false`. Covered in Task 1.
5. **`--out` into a directory that does not exist yet:** the parent directories are created. Covered in Task 2.

  - the Roadmap line "Model type generator from `fields_get` output" ticked (`- [x]`).
- Test: `tests/unit/typegen.command.test.ts`

**Interfaces:**
- Consumes: `generateTypesFile` from Task 1, and `OdooConnect` / `OdooConfig` / `OdooError` from the package.
- Produces:

```ts
export interface TypegenDeps {
  connect: (config: OdooConfig) => Promise<{ orm: { fieldsGet(model: string, attributes?: string[]): Promise<OdooFieldsGet> } }>;
  writeFile: (path: string, content: string) => Promise<void>; // creates parent dirs
  stdout: (text: string) => void;
  stderr: (text: string) => void;
}
export async function runTypegen(argv: string[], env: Record<string, string | undefined>, deps?: Partial<TypegenDeps>): Promise<number>;
```

- `cli.ts` is exactly: a `#!/usr/bin/env node` shebang, then `process.exitCode = await runTypegen(process.argv.slice(2), process.env);`.
- argv grammar: `typegen <model...> [--out <file>] [--help]`. The first positional must be `typegen`. Use `parseArgs` with `strict: true` and `allowPositionals: true`.
- The default `connect` is `OdooConnect.connect`, with config `{ url, db, username, password | apiKey, protocol: apiKey ? "xmlrpc" : "jsonrpc", version }`. `version` is `Number(ODOO_VERSION)` when set and must be an integer from 14 to 19, otherwise a usage error. The default `writeFile` runs `mkdir(dirname(path), { recursive: true })` before `fs.writeFile`.

### Task 3: Publish to GitHub Packages

**Files** (branch `ci/github-packages` from `main`):
- Modify: `.github/workflows/publish.yml`, adding a job after `publish-npm`
- Modify: `README.md`, adding an "Install from GitHub Packages" subsection under Installation
- Modify: `CONTRIBUTING.md` "Releasing", adding one line: after the first GitHub Packages publish, set the package's visibility to public (Package settings → Danger Zone → Change visibility).

**The job:**

```yaml
  publish-github:
    name: Publish to GitHub Packages
    runs-on: ubuntu-latest
    needs: publish-npm
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24.x
          registry-url: https://npm.pkg.github.com
          scope: "@vvhybe"
      - run: npm ci
      - run: npm publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

- Job-level `permissions` replace the workflow's, so there is no `id-token` here and npm does not try OIDC against GitHub's registry.
- `create-release` keeps `needs: publish-npm`.

**README install text:** an `.npmrc` with `@vvhybe:registry=https://npm.pkg.github.com` and `//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}`, using a classic personal access token with `read:packages`. Point out that npmjs.com needs none of this.
